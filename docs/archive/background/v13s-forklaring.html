v13s & d14k: modell, API og veien videre

Forklaring for teamlead. Basert på koden i nais/v13s og nais/api (main) og dokumentasjonen til Dependency-Track v5. Hold musen over understrekede ord for å se hva forkortelsene betyr.

Kort fortalt

1
Action

Bygger imaget, lager SBOM med Trivy og signerer den med cosign som en attestasjon.

2
d14k

Dependency-Track. Tar imot SBOM-en og vet hvilke komponenter imaget består av. Henter sårbarhetsdata fra mange kilder og matcher dem mot komponentene. Resultatet er findings.

3
v13s

Kobler findings til det som faktisk kjører (cluster/namespace/workload). Beriker med KEV og fix-versjon fra OSV, regner ut prioritet og score, lagrer historikk og eksponerer et gRPC-API.

4
nais api

Oversetter v13s til GraphQL for Console, CLI og MCP. Legger på egne beregninger: URGENT (eksponering), trend og «priority groups».

Navnene

v13s = vulnerabilities, med 13 bokstaver imellom. d14k = dependency-track, med 14 tegn imellom (bindestreken teller med). Det er samme mønster som k8s og i18n.

Det viktigste å ta med seg

Dette er fakta i dag. Hvilken komponent (purl) som finnes i hvilket image. Hvilken sårbarhet (CVE/GHSA) som treffer den, med alvorlighetsgrad, CVSS, EPSS og om den står i en KEV-katalog. I tillegg fix-versjon og hvor imaget kjører.
Dette beregner vi i dag («gjetninger»). priority HIGH/ELEVATED/MONITOR, som er terskler på EPSS og KEV. risk_score = 10·critical + 5·high + 3·medium + 1·low + 5·unassigned. top_priority, workload-tellinger per prioritet, coverage og MTTF. I nais api i tillegg URGENT og riskScoreTrend.
Forslaget i én setning. d14k blir sentral og eier sårbarhetsdata, matching, dedup og vurderinger (suppression som regler). v13s blir et tynt, Nais-formet lag som eier «hva kjører hvor» og leverer rene fakta og søk gjennom et API uten egne vurderinger. Detaljene står under Forslag.

Merk. En «sårbarhet» i v13s-APIet (Vulnerability) er egentlig et finding: én CVE i én pakkeversjon i ett image:tag. Cve er sårbarheten i seg selv. Ordbruken er litt forvirrende og er verdt å rydde i et nytt API (Finding vs Advisory).

APIet i dag

Det er to lag: v13s gRPC (internt, per tenant) og nais api GraphQL (det teamene ser i Console, CLI og MCP). Fanen viser hva som eksponeres og hvor beregningene sniker seg inn.

Suppressions: hvordan det virker i dag

En suppression betyr: «Vi har vurdert dette funnet og vil ikke telle det med eller varsles om det.» I bransjen kalles dette en analyse/vurdering, og standardformatet for å utveksle dem er VEX.

Sekvens: en utvikler trykker «suppress» i Console

Nøkkelen bestemmer hvor lenge en suppression varer

I v13s lagres en suppression med nøkkelen (image_name, package, cve_id). package er en full purl med versjon, for eksempel pkg:maven/org.yaml/snakeyaml@1.33. Image-tag er ikke med i nøkkelen. Velg et scenario:

Problemer med dagens modell

To sannhetskilder

v13s-tabellen er fasit, og DT får en kopi via updateren (inntil 4 t forsinkelse). DT lagrer analysen per prosjekt (image:tag), så hver ny tag får en ny kopi. Drift er mulig, og en suppression gjort direkte i DT-UI blir overskrevet eller ignorert.

Feil granularitet

Én rad per image+pakkeversjon+CVE. Det går ikke an å si «CVE-X i snakeyaml <2.0 er ikke relevant for hele team Y» eller «for alle imagene våre». En patch-bump som fortsatt er sårbar nullstiller suppressionen.

Ingen livsløp

Ingen utløpsdato, ingen ny vurdering og ingen «forslag → godkjent». suppressed_by er fritekst. Historikk finnes bare i activity-loggen i nais api.

Fattig semantikk

Tilstand finnes (in_triage/resolved/false_positive/not_affected), men ikke VEX-justification (som code_not_reachable), og ikke evidens eller lenke til analyse. En agent har dermed ingen strukturert måte å si hvorfor.

Hvordan det kan løses

DT v5 har innført vulnerability policies: regler skrevet i CEL som evalueres hver gang et prosjekt analyseres. En regel kan treffe mange findings, også i fremtidige prosjekter. Den kan ha gyldighetsvindu (validFrom/validUntil) og reverteres automatisk når den utløper eller slettes. Den har modus APPLY/LOG/DISABLED og kan synkes fra et Git-styrt bundle.

# Skisse (syntaks ikke testet): en "vurdering" fra Nais, oversatt til DT v5-policy
name: nais/team-foo/CVE-2022-1471-snakeyaml
condition: |-
  vuln.id == "CVE-2022-1471"
  && component.name == "snakeyaml" && component.matches_range("vers:maven/<2.0")
  && "team:foo" in project.tags          # scope: hele teamet, alle images, også fremtidige
analysis:
  state: NOT_AFFECTED
  justification: CODE_NOT_REACHABLE
  details: "Vi deserialiserer aldri ikke-betrodd YAML. Agent-analyse: <lenke>. Godkjent av: kari@…"
  suppress: true
validUntil: 2027-04-01T00:00:00Z         # tvinger ny vurdering
Hvorfor det passer. Én sannhetskilde: regelen bor i DT, og v13s leser utfallet som fakta på findingen (analysis.state, suppressed, policy_id). Scope kan være tenant, team, image eller versjonsrekke. Utløp og revertering er innebygd. Policies passer sammen med VEX, og DT kan eksportere VEX.
Må verifiseres. (1) Policies er globale i DT og krever POLICY_MANAGEMENT, så Nais/v13s må være portvokter: et team kan bare lage regler som er scopet til egne prosjekter. (2) Ytelse med tusenvis av regler × mange prosjekter. (3) Bundle støtter bare én kilde, så Nais-regler må opprettes via API som «user policies», eller vi eier bundlet selv. (4) Prosjekt-tags (tenant/team) må settes konsekvent ved opplasting.

Agent-flyt: «rydd i appen min»

Agenten bruker Nais MCP, som går mot APIet. Den resonnerer selv, mens APIet bare leverer fakta og tar imot forslag.

Forslag: ansvar og API

Ansvarsfordeling

Prinsipper for det nye APIet

1. Fakta, ikke vurderinger

Lever severity, cvss, epss, kev, fix og first_seen slik de er. Fjern priority, risk_score og top_priority. Klienter, Console og agenter rangerer selv. Hvis Console trenger en standardsortering, kan den ligge i klienten eller være en dokumentert filterkombinasjon som kev=true OR epss_percentile>=0.95.

2. Rene ressurser

Workload → Image → Finding (= Component × Advisory) → Assessment. Ett navn per begrep, og Finding er ikke det samme som Advisory. Images identifiseres med digest, med tag som etikett.

3. Aggregater = tellinger

Tellinger med group_by (severity, kev, fix_status, team) er mekaniske og greie å ha. Vektede scorer og terskelbaserte nivåer er ikke det. Historikk leveres som hendelser (appeared/resolved/assessed). MTTF kan avledes av klienten.

Sentral d14k: fordeler og risiko

  

    
Fordeler
    
      
  • Én DT i stedet for én per tenant, så små tenants slipper overhead.
    • 
      
  • Én plass for vuln-feeds, mirroring, oppgradering og drift.
    • 
      
  • v5 skalerer horisontalt (stateless API-servere, PostgreSQL-køer, ingen Kafka) og har retention for gamle prosjektversjoner.
    • 
      
  • Felles vurderinger kan gjelde på tvers. Eksempel: Nais-baseimages vurderes én gang for alle tenants.
    • 
    

    
Risiko og åpne spørsmål
    
      
  • Tenant-isolasjon. Portfolio access control er ute av beta i v5. Hver tenants v13s kan få en DT-team-nøkkel som bare ser prosjekter med tenant:x. Dette må testes, og vi må avklare om noen tenants har krav om dataisolasjon.
    • 
      
  • Blast radius. Hvis den sentrale DT-en går ned, er alle tenants uten data. Kan dempes ved at v13s cacher siste kjente funn.
    • 
      
  • Policies er globale. Autorisasjonen må ligge i v13s/nais api.
    • 
      
  • Migrering. v4 → v5 er en offline engangsmigrering. Alternativet er å starte på nytt og la v13s laste opp alle SBOM-er på nytt, noe som går greit når SBOM-ene ligger i registryet.
    • 
    

  


  
Skal v13s beholde en kopi av findings?

  

    
A. Tynn proxyenklest å forstå
v13s lagrer bare workload ↔ image ↔ DT-prosjekt og spør DT ved lesing.
− Tenant-brede spørringer og filtre (KEV, team) blir mange DT-kall. − Historikk må hentes fra DT-metrics. − Sårbart for DT-nedetid.

    
B. Slank lesemodellanbefalt
v13s speiler findings og analysestatus som rene fakta fra DT og lagrer runtime-kobling og hendelseshistorikk. Ingen egne vurderinger og ingen egen suppression-tabell.
+ Raske tenant-søk og stabilt API. + Overlever DT-nedetid. − Fortsatt synk, men bare én vei (DT → v13s).
