Slå av for å prøve oppførselen uten TTY. Endringer lagres bare i denne siden.

  
Prøv «Vurder» og «Velg pakke». CVE-20XX-0002 finnes bare i lodash og trenger ikke et pakkevalg. CVE-20XX-0001 finnes i både netty-codec-http2 og netty-handler i bestilling. Da må du velge én pakke før noe lagres. Console viser endringen med en gang.

  
Bare severity, ID, installert pakke og kjent fiks i standardlisten. CVE-søk viser CVSS, EPSS og KEV én gang, over de berørte workloadene. JSON beholder alle fakta. Mocken bruker dataene fra Console over, uten nettverk eller shell.

  

    Filtre, JSON og brudd med dagens kommandoer
    
--severity high, --fixable og --kev avgrenser funnene. --suppressed include|only viser vurderte funn.

    
suppress krever vurderingstype og begrunnelse. Pakken finnes automatisk ved ett treff. Ved flere treff spør CLI-en; --package <pakkenøkkel> velger eksplisitt og hopper over spørsmålet. Uten TTY, eller med JSON-output, gir tvetydige treff en feil med alternativene. Ingen «velg alle» eller spredning til andre workloads.

    
unsuppress slår opp lagrede vurderinger, ikke bare aktive funn. Samme regel for pakkevalg gjelder. En vurdering kan derfor fjernes etter at pakken er oppdatert eller funnet er borte.

    
list --output json gir scope, summary, coverage og findings; skrivekommandoene gir resultatet av endringen. Ingen spørsmål eller advarsler blandes inn i JSON. Manglende SBOM og feil ved rescan varsles på stderr; backendfeil gir nonzero exit.

    
Dette er en ny kommandoflate. Dagens summary, list summary og list all tas ut. Workload-kommandoene ligger under app vuln og job vuln, ikke omvendt. Team-/miljø-/output-flagg gjenbrukes; funnfiltre og skrivekommandoer er nye forslag.

    
Skriv nais vuln --help i mocken for syntaks og flagg. Mocken henter to funn per simulert side og tar med alle sider. API-kallene vises nedenfor; pagineringen trenger ingen egen CLI-kommando.

Funn, antall og dekning er tre ulike lesinger

  
findings returnerer radene. summary teller alle radene som matcher samme filter, ikke bare den viste siden. coverage teller workloads med og uten analyseresultater og tar derfor ikke et funnfilter.

På Workload legges vulnerabilityFindings, vulnerabilitySummary og vulnerabilityCoverage. De bruker samme implementasjon som root-feltene. Team-siden summerer over teamets workloads; den får ingen egen risikomodell.

  

    SDL-utdrag: operasjoner, filtre og resultattyper
    
Forslag, ikke dagens schema. Connection- og payload-typer er forkortet. Eksisterende Workload, Slug, Time og Cursor gjenbrukes.

    
extend type Query {
  vulnerabilityFindings(scope: VulnerabilityScopeInput, filter: VulnerabilityFindingFilter,
    first: Int, after: Cursor): VulnerabilityFindingConnection!
  vulnerabilitySummary(scope: VulnerabilityScopeInput,
    filter: VulnerabilityFindingFilter): VulnerabilitySummary!
  vulnerabilityCoverage(scope: VulnerabilityScopeInput): VulnerabilityCoverageCounts!
  vulnerability(identifier: String!): Vulnerability
  vulnerabilitySuppressions(scope: VulnerabilityScopeInput, filter: VulnerabilitySuppressionFilter,
    first: Int, after: Cursor): VulnerabilitySuppressionConnection!
}

extend interface Workload {
  vulnerabilityFindings(filter: VulnerabilityFindingFilter,
    first: Int, after: Cursor): VulnerabilityFindingConnection!
  vulnerabilitySummary(filter: VulnerabilityFindingFilter): VulnerabilitySummary!
  vulnerabilityCoverage: VulnerabilityCoverage!
}

input VulnerabilityScopeInput {
  teams: [Slug!]
  environment: String
  workload: String
}

input VulnerabilityFindingFilter {
  vulnerabilityIdentifier: String
  package: String
  severities: [VulnerabilitySeverity!]
  onlyWithFix: Boolean = false
  onlyKnownExploited: Boolean = false
  suppressed: SuppressedFilter = EXCLUDE
}

enum SuppressedFilter { EXCLUDE INCLUDE ONLY }
enum VulnerabilitySeverity { UNKNOWN LOW MEDIUM HIGH CRITICAL }

type VulnerabilitySummary {
  totalFindings: Int!
  countsBySeverity: VulnerabilitySeverityCounts!
  fixableFindings: Int!
  knownExploitedFindings: Int!
}

type VulnerabilityCoverageCounts {
  totalWorkloads: Int!
  scanned: Int!
  pending: Int!
  noSbom: Int!
  failed: Int!
  unresolvedImage: Int!
}

type VulnerabilityCoverage {
  status: VulnerabilityCoverageStatus!
  imageName: String
  imageDigest: String
  scannedAt: Time
  scannedDbVersion: Time
  error: String
}

enum VulnerabilityCoverageStatus {
  PENDING SCANNED NO_SBOM FAILED UNRESOLVED_IMAGE
}

enum VulnerabilitySuppressionState {
  NOT_AFFECTED FALSE_POSITIVE ACCEPTED_RISK
}

input VulnerabilitySuppressionKeyInput {
  environment: String!
  workload: String!
  imageName: String!
  packageKey: String!
  vulnerabilityIdentifier: String!
}

input NewVulnerabilitySuppressionInput {
  key: VulnerabilitySuppressionKeyInput!
  state: VulnerabilitySuppressionState!
  reason: String!
}

input SetVulnerabilitySuppressionsInput {
  team: Slug!
  items: [NewVulnerabilitySuppressionInput!]!
}

input DeleteVulnerabilitySuppressionsInput {
  team: Slug!
  keys: [VulnerabilitySuppressionKeyInput!]!
}

extend type Mutation {
  setVulnerabilitySuppressions(input: SetVulnerabilitySuppressionsInput!):
    SetVulnerabilitySuppressionsPayload!
  deleteVulnerabilitySuppressions(input: DeleteVulnerabilitySuppressionsInput!):
    DeleteVulnerabilitySuppressionsPayload!
}

  

  

    Regler for telling, filtrering og vurderinger
    
    
      
  • Ett funn er sårbarhet × full purl × workload. Samme image brukt av to workloads gir to forekomster. Vi viser ikke antall unike CVE-er som om det var antall funn.
    • 
      
  • Scope er team, miljø og eventuelt workload-navn. Et workload-navn krever ett konkret team og miljø. En tom teamliste avvises; utelatt teamfilter betyr tenant-bred lesing.
    • 
      
  • Funnfiltre gjelder både liste og opptelling. Dekningen følger bare scope. EXCLUDE er default. INCLUDE brukes for å finne andre berørte workloads, også de som er vurdert.
    • 
      
  • Nye funn- og vurderingslister har first/after og hasNextPage/endCursor. Ingen sideindeks, obligatorisk totalCount eller vilkårlig orderBy. Filtrering skjer før paginering.
    • 
      
  • En vurdering gjelder team + miljø + workload + image-repository + versjonsløs pakkenøkkel + sårbarhets-ID. Den overlever versjonsoppdateringer, men arves ikke av andre workloads eller miljøer.
    • 
      
  • API autoriserer alle mål i batchen og setter aktøren fra innlogget bruker. v0s lagrer bare gjeldende state, begrunnelse, aktør og oppdateringstidspunkt. Ingen ny aktivitetslogg.
    • 
      
  • En mislykket rescan kan beholde forrige analyse med SCANNED og en feil. Nytt image får ikke funn fra forrige image som fallback. Ny workload som ennå ikke er observert i v0s vises som PENDING.
    • 
      
  • Backendfeil gir feil, ikke null funn. Ingen klientstyrt freshness-protokoll foreslås. EPSS-score og percentil bruker 0–1 i API-et og formateres som prosent i klienten.
    •

Foreslått rekkefølge

  
    
    
  1. Implementer API-feltene først. Start med dekning, funn og opptelling for én workload. Bruk noen få aggregerte backendkall; ikke hent alle funn eller gjør ett sett kall per workload for å bygge teamoversikten.
    2. 
    
  2. Oppdater Console og CLI mot det nye schemaet. Nye og gamle felter kan eksistere samtidig under utrullingen, men uten et varig kompatibilitetslag.
    3. 
    
  3. Stans gamle writes før migrering. Avklar hvilke workloads gamle image-vurderinger skal gjelde for. Ikke gjør IN_TRIAGE, RESOLVED eller NOT_SET om til ACCEPTED_RISK. Kontroller backup/restore før v0s blir eneste lager for vurderinger.
    4. 
    
  4. Bytt konsumentene og fjern resten. Slett gamle felter, klientkode, issues og v13s/DT-avhengigheter. Varsle CLI-/JSON-brudd og endringer i dokumenterte metrikker. En eventuell rollback må bevare vurderinger som er skrevet i v0s.
    5. 
  

  
Første leveranse bør være én reell workload vist i begge klienter. Deretter teamaggregatet og batchvurderingene. Mockene over er eksempler til bruk i tester, ikke en implementert backend.
